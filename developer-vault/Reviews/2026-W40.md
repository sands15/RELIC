# 2026-W40 주간 개발 회고

9월 28일~10월 4일 회의 시점까지의 협업을 검토했다. 사용자가 개선안과 다음 실제 작업의 공동 실험을 승인하고 회의 종료 및 상세 적용 기록을 요청했다. 이 문서는 확정 합의 요약이며 대화 원문이 아니다. 회의는 완료됐지만 다음 작업의 적용·효과 검증은 미완료다. 프로젝트 결과는 당시 원본 기록을 확인한 것이며 이번 회의에서 제품 검사나 서비스를 재실행하지 않았다.

## 검증된 결과

- **Evelyn — 잘못된 검사 기대값이 UI 결함을 통과시켰다.** 전체 그래프 비율 대신 기존 구현의 서로 다른 X/Y 배율을 정답으로 사용해, 사용자가 세로 타원 변형을 다시 지적해야 했다. 원본에는 공통 배치 계산으로 교정한 source/offline 검사와 이후 controlled-live UI 확인이 있다. 사용자 시각 선호 수용이나 전체 제품 성공으로 확대하지 않는다. 근거: [[Projects/Evelyn]], [9월 29일 원본](obsidian://open?vault=docs&file=worklog%2F2026-09-29)의 `잘못된 테스트 정답·UI 반복 작업 기록과 다음 검사`, `메모리 패널 레이아웃 규격 정립`.
- **Evelyn — 정상 입력 보존 검사가 실제 결함을 찾았다.** 후보 저장 검증을 강화하면서 정상 한국어 표현까지 거절하는 문제가 독립 검토에서 발견됐고, 실제 임시 저장·새 조회의 실패 재현 후 수정됐다. 국소 source/offline 통과와 별개로 당시 전체 영향 검사의 기존 입력 누락 실패는 남았다. 독립 검토가 유용했던 사례이지 반복 검토 전체가 효율적이었다는 증명은 아니다. 근거: [[Daily/2026-10-02]], [10월 2일 원본](obsidian://open?vault=docs&file=worklog%2F2026-10-02)의 `개인 기억 값·항목 관계와 서명 본문 왕복 교정`.
- **Evelyn — 검사 환경과 요구 추적에도 누락이 있었다.** 검사 runner가 실제 설정과 다른 환경변수를 사용해 처음 통과를 격리 증거로 삼을 수 없었다. 별도 요구 대조에서는 표시 순서, 전체 부팅과 단독 복구, 명시적 OFF, 실제 명령 후조건 등 세부 수용 조건을 보강했다. 목록 정합성 검사는 요구 전체 충족이나 숨은 결함 부재의 증거가 아니다. 근거: [9월 29일 원본](obsidian://open?vault=docs&file=worklog%2F2026-09-29)의 `검토에서 발견한 검사 격리 오류` 항목, [10월 2일 원본](obsidian://open?vault=docs&file=worklog%2F2026-10-02)의 `원래 요구의 명시 수용과 core Router 잔여 보강`.
- **개인 작업 방식 — 승인된 개선안을 실제 지침에 반영했다.** Codex 전역 `AGENTS.md`의 기존 요구·실행·검토·완료 절을 수정하고 현재 파일에서 반영을 확인했다. 공개 원본 링크는 없다. 이는 지침 문구 반영의 증거이며 후속 개발 작업의 준수·성능·사용자 경험 개선 증거는 아니다. Evelyn 코드·프로젝트 상태 문서는 이 회의에서 변경하지 않았다.

## 프로젝트 간 배움

- 검사 정답은 구현이 아니라 원래 요구와 보존 조건에서 독립적으로 도출한다. 필요한 경우 최소 반례나 격리된 잘못된 변형이 실제로 실패하는지 확인한다.
- 최소 수정은 줄 수가 가장 적은 땜질이 아니라 원인과 인과적으로 연결된 결함을 닫는 최소한의 완결된 수리다. 작은 진단·회귀와 비용이 큰 본 실험을 구분한다.
- 환경 분리를 주장하려면 보호할 대상을 먼저 정한다. 패키지 분리, 상태 저장 경로, 자식 프로세스의 상속 설정, 운영체제의 파일·네트워크·장치 제한은 서로 다른 경계다.
- 검토가 결함을 찾았다는 사실과 사용자가 기다린 만큼 가치가 있었는지는 별도 평가다. 검토 횟수가 아닌 결과 보존과 반복·대기 부담을 함께 본다.

- 정확한 원본 링크가 있는 결과 수: 프로젝트 근거 3묶음에 원본 2개 문서와 해당 절·항목을 명시했다. Obsidian 링크는 해당 vault가 필요하며 공개 웹 링크가 아니다. 지침 수정은 로컬 파일 대조이며 공개 원본은 없다.
- 뒤늦게 발견한 누락: 프로젝트 색인의 검토일은 9월 4일로 남아 있어 최신 상태의 증거로 삼지 않았다. 기존 10월 4일 Daily가 인용한 R43 원본 절은 회의 종료 시점의 지정 문서에서 찾지 못했다. 그 항목은 이번 성과 판정에서 제외하고 원본 연결 확인을 남긴다. 이번 회의에서 기존 Daily 내용을 임의 교정하거나 확정하지 않았다.
- 기록 시간과 재탐색 절감 효과: 미측정. 대기·반복 부담이 더 컸다는 사용자 평가는 확인했지만, 분 단위 지연이나 특정 도구의 인과적 비용으로 환산하지 않는다.

## 협업 회의

### Codex의 개선 약속

- W39의 기존 기능 보존·근거 구분 합의가 있었지만 잘못된 UI 검사 정답 때문에 사용자의 재지적이 발생했다. 설치된 스킬이나 지침 존재를 적용 성공으로 취급하지 않는다.
- 격리 방식 설명 전에 공식 자료를 확인하지 않은 점을 인정하고 이후 공식 자료를 확인했다. 과거 작업에서도 조사하지 않았다고 단정하지 않는다. 다음 격리 설계·변경 때 실제 설정과 공식 자료를 먼저 대조한다.
- 큰 요구를 짧은 목록으로 옮길 때 실행 순서·취소/OFF·복구·소유권·최종 결과를 누락하지 않는다. 원래 요구와 행동을 양방향 대조하고 불필요한 요구도 추가하지 않는다.
- 실패하면 원인 경로와 공통 경계·관련 호출자·형제 경로를 조사한다. 근거가 지지하는 원인과 가설을 구분하고, 관련 결함을 수리·검증한 뒤 본 실험을 재개한다. 진단에 필요한 작은 검사는 수리 중에도 허용한다.
- 작은 저위험 변경은 직접 확인한다. 비단순·고위험 변경의 독립 검토는 유지하되 관련 수리와 검사를 마치고 넘긴다. 재검토는 수정 부분과 영향 경로에 집중하며 전체 반복에는 구체적 이유를 남긴다.
- 단계마다 재승인을 요구하거나 사용자가 대신 진단하게 하지 않는다. 새로운 설계·정책·권한 등 결과를 바꾸는 선택만 이유·권장안과 함께 질문한다.
- 완료는 최종 산출물의 요구 충족으로 판단한다. PASS·FAIL·BLOCKED·NOT_RUN과 source/offline·controlled-live·운영·사용자 수용을 분리한다.

### 사용자에게 필요한 지시·결정

- 사용자 체감: 독립 검토 과정의 기다림과 반복작업 부담이 더 컸다. 객관적 시간 측정과 구분한다.
- 사용자는 위 개선과 다음 실제 작업 하나의 공동 실험, 회의 종료·상세 기록을 승인했다. Codex가 증거를 수집하고 사용자는 원하는 결과·중요한 선택·최종 체감을 제공한다.
- 이미 제공한 의도를 반복 설명하도록 요구하지 않는다. 작업 중 새로 발견한 보존 조건 충돌은 Codex가 임의로 희생시키지 않고 질문한다.
- 다음 대상은 이후 사용자가 맡기는 실제 승인 작업 하나다. 현재 작업명·작업 링크는 미선정이다. 기존 진행 작업을 임의로 지정하거나 새 기능·실험용 작업을 만들지 않는다.

### 유지·중단·변경 합의

- 유지: [[Reviews/2026-W39]]의 기존 기능 보존과 합의의 실행 의무, 승인 범위 내 자율 수리·재검증, 검증 수준 구분. W37에서 사용자 체감 결함 방지 효과로 유지한 Superpowers는 유지한다.
- 중단: 구현을 그대로 정답으로 채택, 근거 없는 격리 주장, 관련 결함이 남은 상태의 본 실험 반복, 같은 산출물의 이유 없는 검토자 교체·전체 재검토, 단계별 반복 승인.
- 변경: 원래 요구·인과적 수리·최종 사용자 결과를 중심으로 검사와 기록을 묶고, 검토는 필요한 범위에 집중한다.
- 보류 유지: A06 식량 판정 통합을 생존 개선이나 Superpowers 성공 표본으로 세지 않는다. 큰 생존 목표가 행동으로 이어지지 못한 원인 가설·해결책·생존 실험 선정은 이번 회의에서 확정하지 않았다.

- **대상과 권한:** 이후 사용자가 맡기는 실제 승인 개발 작업 하나. 미선정·적용 NOT_RUN. 별도 실험용 기능, 설치, 서비스 기동, 배포 권한을 만들지 않는다.
- **실행:** 그 작업의 기존 계획·작업 기록에 이 회고를 연결하고 적용 가능한 합의를 보존 조건·수용 기준으로 이어간다. 같은 개선의 승인을 다시 묻지 않는다. 관련 없는 항목은 이유를 남기며 수를 채우려고 실행하지 않는다.
- **상세 기록 방식:** 기존 요구별 항목에 (1) 회의 합의와 원래 요구, (2) 실제 적용한 결정·파일·함수·검사 등 식별 가능한 위치, (3) 적용 또는 미적용 사유, (4) 최종 revision과 검증 환경·관측 결과·증거 수준, (5) 남은 문제·담당·다음 조치를 남긴다. 코드·시험 상세와 수치는 프로젝트 원본에 두고 Vault에는 요약과 정확한 원본 링크만 남긴다.
- **재작업 기록:** 실패 원인·연결된 결함·수리 단위와 본 실험을 다시 시작한 근거를 남긴다. 작은 가설 검사를 불필요한 반복과 섞지 않는다. 반복 검사·검토는 직전 결과 이후 무엇이 바뀌었고 무엇을 새로 확인했는지 기록한다. 명령·로그 전문은 복제하지 않는다.
- **대기 기록:** 작업 기록에서 확인 가능한 실행·차단·사용자 결정 대기를 구분한다. 이미 승인된 단계의 재승인이나 근거 없는 재검토가 있었으면 숨기지 않는다. 시간 자료가 없으면 미측정으로 두고 이전 작업 대비 절감 시간을 만들지 않는다.
- **성공 기준:** 알려진 연결 결함을 닫기 전에 본 실험을 무의미하게 반복하지 않고, 이유 없는 검토·검사·재승인 대기가 없어야 한다. 변경에 영향받는 기존 기능과 요청 결과는 필요한 수준에서 검증한다. 빨라져도 기존 기능이 고장났으면 성공이 아니다.
- **체감 평가:** Codex가 근거를 먼저 제시한 뒤 사용자가 기다림과 같은 의도를 반복 설명하는 부담이 줄었는지 평가한다. 기술적 통과와 사용자 체감은 별도로 기록한다. 사용자의 평가나 필수 검증이 없으면 효과 확인을 미완료로 유지한다.
- **후속 연결:** 대상이 정해지면 기존 작업 기록에 작업 식별자·원본 링크를 남긴다. 종료 때 위 항목의 실제 적용 여부를 상세히 정리하고, 다음 회의에서 이 회고와 대조한다. 현재 회의 완료를 공동 실험 완료로 해석하지 않는다.
