# 2026-10-31

## Evelyn 전체 코드 리뷰 (읽기 전용)

마음 개편 이틀 뒤 전체 코드를 읽기 전용으로 리뷰했다. 마음 6,800줄은 직접 정독, 나머지 7개 영역은 병렬 리뷰어가 같은 형식(파일:줄·재현·영향·근거·심각도)으로 조사하고 P1은 내가 코드로 재확인했다. P0 0, P1 18. 세 묶음이 대부분을 설명한다: 옛 Bridge 필드를 요구하는 소비자가 새 몸이 그 필드를 만들지 않아 영구 실패(화자 등록 409, 종료 명령이 플래그만 세움), 마음의 텍스트 대체가 존재하지 않는 몸 이름으로 가서 사라지는 침묵 경로(테스트는 그 이름의 가짜 몸을 접속시켜 통과), 기억 삭제 보장의 빈틈(미러 노트 재생성, 프로세스 내 대화 기록이 삭제를 모름). source/offline, live NOT_RUN, 수리 0. 출처: Evelyn `docs/worklog/2026-10-31.md#code-review-20261031`, 결과 `docs/EVELYN_CODE_REVIEW_2026-10-31_KR.md`.

재사용 가능한 교훈: (1) 큰 교체(한 프로세스를 새 프로세스로 바꾸기) 뒤에는 "옛 쪽이 **만들던** 필드"를 전수로 뽑아 소비자를 역추적해야 한다. 소비자는 테스트 픽스처가 옛 필드를 주입해 주는 동안 녹색으로 남고, 생산에서는 조용히 항상 거부/항상 빈값이 된다. 픽스처가 주입하는 키 목록과 생산자가 쓰는 키 목록을 한 번 diff하면 바로 드러난다. (2) 대체(fallback) 경로는 테스트에서 "존재한다고 가정한 대상"이 생산에도 존재하는지 확인해야 한다 — 가짜 수신자 이름을 하드코딩한 테스트는 대체 경로가 아무 데도 닿지 않아도 통과한다. (3) "삭제했다"는 보장은 저장소 한 층(노트 인덱스)만 보면 안 되고, 그 원문이 흘러간 모든 사본(raw 로그, 미러, 다른 프로세스의 메모리 내 이력)을 같은 삭제 원장으로 거르는지 세어 봐야 한다. (4) 리뷰어 여러 명의 결과를 합칠 때는 같은 원인이 영역마다 다른 증상으로 보고되므로(fence digest → 미리보기·`/mic on`·마이크 테스트), 결함을 증상 수가 아니라 원인 묶음으로 정렬해야 우선순위가 맞는다.

## Evelyn 리뷰 수정 1~8번 묶음 (같은 날 오후)

오전 리뷰의 P1 18건을 같은 원인끼리 12묶음으로 묶은 계획을 쓰고, 소유자 결정 다섯 가지(대화 기억 회상 재개, 부팅 때 마이크 강제 ON 제거, 소유자 연결 교체는 클릭으로만, 능력 줄은 실제 마음 상태, Discord 유지)를 받아 1~8번 묶음을 하루에 수리했다. 매 묶음은 실패 테스트 → 수리 → 좁은 검사 → 커밋 → 작업 기록 순서로 갔고, 1·3·5·8번 뒤 전체 회귀(약 7,400건)와 재기동·닥터 live를 돌렸다. live로 확인한 것: 화자 등록 차단 해제, 두 번째 브라우저가 소유자 연결을 훔치지 않고 "옮기기" 버튼을 보임, `/shutdown`이 Host Supervisor 경로로 16초 안에 전부 내려감, 런처가 마음 `/health`를 기다림. 출처: Evelyn `docs/worklog/2026-10-31.md`(`#bundle1-old-bridge-consumers-20261031` ~ `#bundle8-dead-code-1-20261031`), 계획 `docs/plans/2026-10-31-code-review-fix-plan.md`.

재사용 가능한 교훈: (1) 컨테이너의 단조 시계는 호스트 재부팅으로 다시 시작한다 — "최근 실행"을 시각으로 가르면 재부팅 뒤 실행이 사라지고 옛 실패가 최근 것으로 보인다. 실행 경계는 시각이 아니라 프로세스가 매번 1부터 세는 revision 같은 재시작 표식으로 가른다. (2) 안전 필터를 더 느슨하게(허용을 늘리는 쪽으로) 바꿀 때는 캐시 키·정책 문자열을 올릴 필요가 없다 — 옛 규칙으로 만든 캐시·영수증은 새 규칙에서도 유효하다. 올렸더니 정책 문자열을 고정한 픽스처 6곳이 읽기 lease 안에서 정책 이전을 시도해 테스트가 교착했다. 정책 문자열은 허용을 줄일 때만 올린다. (3) 테스트가 소스를 AST로 추출해 이름 목록으로 네임스페이스를 만드는 구조에서는, 새 도우미 함수를 추가하면 호출자 함수가 추출돼도 도우미가 없어 `NameError`가 난다 — 추출 목록을 함께 고치고, 그런 테스트가 있는 모듈에서는 도우미 추가를 작게 한다. (4) 수정 스크립트와 테스트와 커밋을 한 셸 체인으로 묶을 때, 중간 단계가 실행되지 않아도 다음 단계가 이어지면 빨간 테스트가 커밋된다. 커밋 직전에 결과 파일을 다시 읽어 실패·미완료가 있으면 멈추는 게이트를 체인 안에 둔다. (5) 큰 함수 치환 패치는 "다음 `def`까지" 잘라내기 쉬운데, 일반 함수와 `async def`가 섞인 파일에서는 그 사이 함수가 함께 지워진다. 치환 뒤 지워진 정의 목록(`git diff`의 `-def`)을 확인한다. (6) 두 창이 같은 소유자 연결을 다투는 기능은 자동 재시도와 상극이다 — 재시도 루프는 "일시적 실패"에만 두고, 사람이 결정해야 하는 상태(다른 창이 연결됨)는 재시도를 멈춘다.

## Evelyn 음성 진단 제거 (같은 날 저녁)

사용자가 멈춘 개발용 음성 진단(voice-p0)을 "제거해"로 결정해, 모듈·라우트·패널·테스트와 그에 기댄 분기(동의 관리자의 진단 범위, 감독자의 재시작 억제, Discord 입력·TTS의 시도 결속 검사, 관측 관찰자)를 한 번에 지웠다(약 11,000줄). 원본은 프로젝트 `docs/worklog/2026-10-31.md#voice-diagnostic-removed-20261031`.

재사용 가능한 교훈: (1) 기능 하나를 지울 때는 "그 기능이 만들던 값"을 읽는 쪽을 전부 찾아야 한다 — 여기서는 진단이 쓰던 세션 상태를 동의 관리자·감독자·TTS가 각자 읽어 분기했고, 모듈만 지우면 import 오류로 드러나지만 상태 키만 남는 분기(`validation_*` 메타)는 조용히 죽은 코드가 된다. 삭제 경계는 "import가 끊기는 곳"과 "값이 사라져 항상 같은 길로 가는 분기"로 나눠 전자는 지금, 후자는 목록으로 남겼다. (2) 영속 레코드에서 필드를 뺄 때 스키마 문자열만 올리면 옛 파일이 전부 복구 경로로 들어간다. 이번에는 그 복구가 마이크 스위치를 끄는 경로였고, 테스트가 아니라 재기동 뒤 로그에서야 보였다. 뜻이 같은 옛 레코드는 읽을 때 새 스키마로 옮기고, 뜻이 달라진 것만 복구로 보낸다(정정: 처음에는 "복구 1회면 된다"고 적었다). (3) 큰 테스트 파일을 반쯤 지울 때는 AST로 메서드를 지우고, 치환 전에 삭제·치환 순서를 고정해야 한다 — 내가 넣은 새 테스트 문장이 뒤의 전역 치환에 걸렸다.

## Evelyn 배경 작업 답 채팅 전용·옛 전달 사슬 삭제 (같은 날 밤)

사용자가 배경 작업 답을 "채팅에만" 두기로 결정해, Bot API가 그 답을 아무도 꺼내지 않는 발화 큐에 넣던 세 곳과 재생 영수증을 지웠다. 같은 묶음의 남은 죽은 코드(넣는 쪽이 없는 옛 전달 확인 사슬, 항상 빈 임시 답변 말풍선, no-op `stop-proactive`)도 지웠다. 원본은 프로젝트 `docs/worklog/2026-10-31.md#background-answers-chat-only-20261031`, `#bundle8-step3-20261031`.

재사용 가능한 교훈: (1) "A로 할까 B로 할까" 질문은 먼저 그 기능이 어디서 시작되는지를 호출 그래프로 확인하면 답이 거의 정해진다. 배경 작업은 타이핑으로만 시작돼 "글엔 글로 답한다"는 기존 규칙과 맞는 쪽이 분명했다. (2) 빌드가 작업 트리를 이미지로 복사하는 동안에는 테스트 파일도 고치지 않는다. `.dockerignore`가 `tests/`를 넣고 있어, 커밋에 없는 변경이 그 revision 라벨이 붙은 이미지에 섞일 수 있다. 기다리는 동안은 패치 스크립트를 저장소 밖에 준비했다.
