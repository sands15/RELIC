# 2026-11-14

## [[Projects/Sephiria Optimizer|Sephiria Optimizer]] — 게임이 올라가면 새 파일로 다시 빌드하는 것부터 한다 (v0.4.8)

게임이 1.0.33에서 1.1.3으로 올라간 날, 설치된 도구(v0.4.5)와 미설치 v0.4.7이 모두 새 게임에서 쓸 수 없는 상태인 것을 찾았다. 도구가 참조하던 게임 클래스 하나가 이름과 구조를 바꿔 사라졌기 때문이다. 버전 문자열로 막지 않는 호환 정책은 그대로였지만, 사라진 클래스를 참조하는 메서드는 통째로 실행되지 않는다.

v0.4.8로 고쳐 설치했다. 바뀐 위치 효과 부적의 구조와 규칙, 신규 부적 2종을 반영했고, 게임 1.1에서 켜진 배치 보너스를 보호한다(붙이면 합쳐지는 조합은 추천과 적용 중간 단계 어디에서도 새로 붙이지 않고, 이미 성립한 묶음은 유지). 게임을 켤 때마다 남던 프로세스별 파일은 시작할 때 정리하고, 설치 백업은 최근 5개만 남긴다.

배운 점은 다섯 가지다.

- 게임 업데이트 직후 점검은 새 게임 파일로 플러그인을 다시 빌드하는 것에서 시작한다. 깨진 참조가 컴파일 오류로 바로 나온다. 그다음 참조 전수 대조, 디컴파일 비교로 규칙 변화를 본다.
- 선택적인 게임 타입은 작은 메서드 하나에 가두고 호출하는 쪽에서 로드 실패를 받는다. 그래야 다음에 이름이 바뀌어도 해당 아이템만 일반 처리로 떨어지고 나머지 읽기는 계속된다.
- 되돌릴 수 없는 게임 동작(아이템 합성)은 최종 배치만이 아니라 적용 중간 단계 전부에서 막아야 한다. 한 번에 한 칸씩 옮기는 동안에도 게임은 매번 규칙을 다시 평가한다.
- 옛 규칙을 전제로 한 시험이 실패하면 기대값만 바꾸지 않는다. 같은 의도(위치 피해를 잃는 추천 금지)를 새 전제에서 다시 구성하고, 제약이 없으면 실제로 움직인다는 대조 시나리오를 함께 둔다.
- 실행마다 프로세스 ID가 붙은 파일을 만드는 도구는 만드는 쪽에서 치우는 시점도 정해야 한다. 석 달 동안 800개 가까이 쌓여 있었다.

적용: [[Learnings/Evidence scope is part of the result]]의 증거 범위 구분(게임 파일 대상 오프라인 검사와 타이틀 화면까지의 실행은 확인, 실제 플레이는 미확인).

증거 수준: 게임 1.1.3의 실제 DLL과 에셋을 대상으로 한 오프라인 검사가 모두 통과했다(부적 데이터 15종 읽기, 실제 게임 클래스로 부적 읽기, 능력치 계산식 대조 5건, 합성 가방 514건의 적용 순서 검사, 전체 자체 검사, 설치기 검사). 게임을 타이틀 화면까지 실행해 플러그인 0.4.8 로드, 보조 프로그램 기동, 남은 파일 797개 정리를 확인했다. 런을 플레이하지 않았으므로 실제 가방에서의 추천과 추천 적용은 미확인이다. 전용 Git 저장소가 없는 로컬 산출물이다.

같은 날 후속(v0.4.9): 설치 뒤 변경분을 다시 검토해 7건을 찾아 모두 고쳤다. 가장 큰 것은 배치 보너스 묶음이 있는 가방에서 추천이 현재 배치에 머무는 문제였다. 묶음 유지를 마지막 검사에서만 걸러내고, 현재 배치에서 출발하는 탐색은 다른 조건에서만 돌았기 때문이다. 수정 없이 실패하고 수정 뒤 통과하는 큰 가방 시험을 추가했다. 합성 방지는 게임과 같이 기능이 켜져 있을 때만 걸도록 좁혔다. 배운 점 하나를 더한다. 새 제약을 "후보를 거르는 검사"로만 넣으면 탐색이 그 제약을 만족하는 후보를 만들 수 있는지는 따로 확인해야 한다. 작은 시험 가방에서는 우연히 통과했다.

다음 확인: 실제 런에서 가방을 열어 추천이 뜨는지, 추천 적용이 되는지 본다.
