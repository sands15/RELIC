# 2026-11-07

## Evelyn Control Page — 대화 기록은 "읽기 전용" 저장소로 두면 기억 노출 규칙이 하나로 줄어든다

Control Page 대화를 오래 남기고 위로 올려 더 불러오는 기능을 설계해 사용자 승인을 받았다. 먼저 "이블린도 이 기록을 읽는가"를 물었고 사람이 읽는 용도만으로 정해지자, 회상·노출 위치 계산이 빠지고 "삭제된 기억에 기댄 답을 가린다"는 규칙 하나만 남아 설계가 단순해졌다. 저장은 전용 SQLite 하나(원래 시각·고유 ID·소유자 해시), 읽기는 ID 커서, 보존은 기간 제한 없음에 디스크 상한과 사용자 지우기다. 기존 Discord 보관소(30일, 관리자 인증)는 다른 사람의 말이 섞이는 경로의 규칙이라 재사용하지 않았다. 빌더 검토가 소스를 대조해 설계가 모르던 세 가지(되살린 행의 `source`에 기대는 코드, 행을 제거하는 경로 둘, 기억 삭제가 다른 프로세스에서 실행됨)를 찾아 범위에 넣었다. 교훈: 저장소 설계는 "누가 읽는가"를 먼저 정하면 규칙의 절반이 사라지고, 설계 문서는 코드와 대조하는 검토를 한 번 거쳐야 쓰기 경로의 예외가 드러난다. 구현·테스트·라이브는 없다. 원본은 Evelyn `docs/worklog/2026-11-07.md#control-page-transcript-design-20261107`이다.

## Evelyn Control Page — 색만 바꾸지 않고 구조를 바꿔 "모델을 보는 화면"으로 리뉴얼했다

처음엔 CSS 색만 바꿨다가 사용자가 "색깔놀이가 아니다"라며 거부했고, 시안으로 구조(영상 자막 배치, 상반신 모델, 애플 제품 소개 페이지식 절제, 상태 요약 패널, 이블린 크기 조절)부터 고르게 하자 방향이 잡혔다. 구현은 서브에이전트로 작업 12개 중 11개(T0~T11)를 작업마다 구현자와 리뷰어를 따로 두어 진행했고, 마지막 전체 브랜치 리뷰가 단위 리뷰가 못 본 이음새 결함(입력 중 모델 크기 요동, 문서가 검증을 안 했다고 적음)을 찾았다. 헤드리스 Chrome의 진짜 마우스·키보드·핀치 입력으로 검증하니 정적 테스트가 모두 통과한 뒤에도 중요 결함 3건과 사소한 결함 15건이 나왔다(휴대폰에서 마이크 창이 페이지를 넓힘, 태블릿 폭에서 메모리 창이 찌그러짐, 배경 사진 위 자막 대비 부족). 교훈: 시각 리뉴얼은 테스트 통과가 끝이 아니라 실제 입력으로 눈·손 검증을 한 번 해야 하고, 작업별 리뷰가 모두 통과해도 전체 리뷰가 작업 사이의 결합 결함을 따로 찾는다. 증거 한계: 정적 서버·헤드리스 Chrome·CDP 접근성 트리 검증이고 실제 런타임 연결·실제 기기·실제 사진 배경은 미검증이다. agent-desktop은 페이지 내용을 읽지 못했다. 문장 단위 자막 동기화(T12)와 예전 대화 불러오기는 구현하지 않았고, 입력창이 늘어나지 않는 결함(이 브랜치가 만듦)이 남았다. 브랜치 `feat/control-page-redesign`은 병합·푸시하지 않았다. 원본은 Evelyn `docs/worklog/2026-11-07.md#control-page-redesign-20261107`이다. 다음: 병합 여부 결정, 입력창 높이 수정, T12.
