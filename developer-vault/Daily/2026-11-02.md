# 2026-11-02

## Evelyn 마음 운영 경계·운영·닥터 (첫 물결)

9·11번 묶음의 남은 항목을 worktree 여섯 갈래로 나눠 구현하고 갈래마다 반박 검증을 붙였다. 검증이 잡은 가장 큰 결함은 오디오 큐를 도입하면서 생긴 발화 손실이었다. 연결이 끊기면 큐가 버려지는데 몸은 쓰기 반환만 보고 발화를 잊었다. 마음이 처리 뒤 확인을 보내고 몸이 그때까지 보관하도록 바꿨다. 소스·회귀 수준이고 live는 남았다. 원본은 프로젝트 `docs/worklog/2026-11-02.md#wave1-mind-ops-doctor-20261102`.

재사용 가능한 교훈: (1) 쓰기가 끝났다는 것은 상대가 처리했다는 증거가 아니다. 중간에 큐를 넣으면 전달 보장의 경계가 옮겨 가므로 확인 신호를 다시 설계해야 한다. (2) 새 테스트는 수리를 뺀 코드에서 실패하는 것을 봐야 한다. 끝에서 끝 테스트가 수리 없이도 통과해 살펴보니 가짜 소켓이 다른 경우를 재현하고 있었다. (3) Windows의 `time.monotonic()` 눈금은 약 15.6 ms다. 짧은 구간의 겹침을 재는 테스트는 `perf_counter`를 써야 하고, 간헐 실패를 대기 시간 문제로 넘겨짚으면 한 번 더 헛수리를 하게 된다. (4) "답하지 않음"을 경고하려면 "일부러 답하지 않음"이 기록돼 있어야 한다.

## Evelyn 죽은 코드 정리와 기억 인증 (둘째 물결)

죽은 코드 약 53,700줄을 단계별 반박 검증과 함께 지웠고, 기억 색인 인증을 파일 이미지에서 행 지문으로 바꿨다. 병합 트리 전체 회귀는 나쁜 결과 0이었고, 재빌드 기동은 3분 20초, 닥터 live는 2회 FAIL 0이었다. 원본은 프로젝트 `docs/worklog/2026-11-02.md#wave2-dead-code-memory-20261102`.

재사용 가능한 교훈: (1) 이름 검색으로 "호출자 없음"을 판정하면 기본값이 아닌 분기의 호출을 놓친다. 삭제 뒤 정의되지 않은 이름 검사를 별도로 돌린다. (2) 삭제하는 테스트의 단언을 하나씩 읽는다. 남는 코드의 유일한 검사가 섞여 있다. (3) SQLite 파일 이미지는 내용의 지문이 아니다. 같은 내용이어도 헤더와 빈 페이지가 다르다.

## Evelyn 잔여 결함과 소유자 결정 목록 (셋째 물결)

둘째 물결 검증이 남긴 지적을 닫고, 소스로 닫을 수 없는 항목을 프로젝트의 결정 목록으로 모았다. 전체 회귀는 549모듈·6,848테스트 나쁜 결과 0이고, 재빌드 기동은 3분 1초, 닥터 live는 2회 FAIL 0·WARN 2다. WARN은 출력 장치와 삭제 승인 대기 임시 파일이다. 작업자 `main.py`는 Discord live 없이 오프라인 구동으로만 확인했다. 원본은 프로젝트 `docs/worklog/2026-11-02.md#wave3-residual-fixes-20261102`.

재사용 가능한 교훈: (1) 고치는 조건은 관찰한 증상보다 넓어지기 쉽다. "실행 중"을 "멈춤"으로 읽은 첫 수리가 정상 회상을 저하로 표시했다. (2) 시작 순서의 앞 단계 실패가 뒤 단계를 막는지 실패 주입으로 구동해 본다. 이벤트 처리기의 예외는 프로세스를 죽이지 않아 재시작 정책도 돕지 못한다.

## Evelyn 요청 처리기 구동 (넷째 물결)

라이브 GET 점검이 권한에서 멈춘 것을 보고 실제 aiohttp 앱을 합성 토큰으로 오프라인 구동했다. 호출어 없는 음성이 답을 지우던 문제, Discord READY 재시도의 빈틈, 몸 상태의 거짓 진단 오류, 공백·한글 쿼리의 서명 실패를 찾아 고쳤다. 전체 회귀는 550모듈·6,863테스트 나쁜 결과 0이다. 원본은 프로젝트 `docs/worklog/2026-11-02.md#wave4-handler-drive-20261102`.

재사용 가능한 교훈: (1) 5xx가 없다는 라이브 점검은 권한 뒤의 코드를 말해 주지 않는다. 403 비율을 함께 본다. (2) 공용 도우미로 입력 검사를 통합하기 전에 호출부가 이미 가진 고유 오류 코드를 확인한다. (3) 서명은 전송되는 바이트와 같은 표현에 걸어야 한다.

## Evelyn 턴 겹침과 Discord 보관 (다섯째 물결)

답을 끊는 범위를 대화 단위로 좁히자 두 답이 동시에 돌게 됐고, 그 순간 숨어 있던 가정이 줄줄이 드러났다. 먼저 온 순서의 Main 대기열, 전역 가설, 턴 하나를 전제한 기억 짝짓기다. 공유 턴을 하나로 묶고 소유자가 선점하게 했으며, Discord 텍스트 보관과 `feedback`을 다시 연결했다. 전체 회귀는 561모듈·7,038테스트 나쁜 결과 0, 닥터 live는 2회 FAIL 0이다. Discord와 마이크 live는 하지 않았다. 원본은 프로젝트 `docs/worklog/2026-11-02.md#wave5-overlap-archive-20261102`.

재사용 가능한 교훈: (1) 동시성을 하나 열면 "한 번에 하나"를 전제한 코드를 전부 다시 본다. 취소가 그 전제를 지켜 주고 있었다. (2) 게이트 규칙을 바꿀 때는 게이트를 거치지 않는 길을 찾는다. 연결 단위 일괄 취소가 규칙을 우회하고 있었다. (3) 개인 정보를 쓰는 경로는 수리 뒤 반드시 삭제·철회와 경쟁시켜 본다. 네 번의 반박 검증이 모두 실제 결함을 찾았다. (4) 따로 만든 두 갈래를 합칠 때는 만나는 지점만 보는 검증을 한 번 더 둔다.

## Evelyn 보관 삭제의 끝까지 (여섯째 물결)

보관 삭제가 마음의 대화 기록까지 닿게 하고, 소유자 우선을 TTS와 회상까지 넓혔다. 전체 회귀는 563모듈·7,164테스트 나쁜 결과 0, 닥터 live는 2회 FAIL 0이다. 삭제 경로는 실제 Discord와 실제 보관 배포로 확인하지 않았다. 원본은 프로젝트 `docs/worklog/2026-11-02.md#wave6-delete-owner-20261102`.

재사용 가능한 교훈: (1) 필수 정리 단계를 재시도 루프에 넣을 때는 그 단계의 부작용이 반복돼도 되는지 먼저 본다. 삭제 프레임이 1초마다 라이브 턴을 지울 뻔했다. (2) "캐시는 어떤 보존 기한보다 젊다" 같은 가정은 코드로 확인한다. 실제로는 나이 제한이 없었다. (3) 따로 만든 갈래를 합친 뒤에는 한쪽이 바꾼 이름을 다른 쪽이 쓰는지부터 본다. 삭제 실패가 안전한 쪽으로 난 것은 다행이었다.

## Evelyn Terraria 동료 몸 사전 분석

REA와 ILSpy로 사용자 소유 Terraria 1.4.5.8을 정적 분석해 이블린이 Host & Play 월드에 TCP로 따로 들어올 수 있음과 보스 상태가 네트워크로 보임을 확인했다. 구현은 아직이며 방식 선택 대기다. 원본은 프로젝트 `docs/worklog/2026-11-02.md#terraria-body-analysis-20261102`.

재사용 가능한 교훈: (1) 사용자가 이름으로 말한 도구는 스킬 레지스트리보다 GitHub의 원래 프로젝트부터 찾는다. 레지스트리의 비슷한 이름은 다른 것이었다. (2) 게임 봇은 클라이언트가 자기 피격·위치를 정하는지 먼저 본다. 서버가 믿어 주는 값이면 봇이 그 계산을 직접 돌려야 정직한 플레이가 된다. (3) 이름에 "codex"가 붙은 경로가 실제로 Codex를 부르는지 코드로 확인한다. 이번에는 로컬 모델로 가고 있었다.
