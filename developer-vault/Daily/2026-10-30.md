# 2026-10-30

## Evelyn Mind 옛 Bridge 정리와 기능 복원

옛 Bridge 상태를 받던 묶음에서 아무도 호출하지 않는 라우트와 상태 POST 경로를 지웠다(약 700줄). 지우다가 Control Page의 화면·선제 동의 스위치가 소유자를 옛 상태에서 알아내던 탓에 항상 거부되고 있음을 발견해, 몸의 서명된 상태 파일에서 소유자를 읽도록 고쳤다. 환영 문구·도구 결과 설명·방송 채팅 선택은 마음 요청으로 옮겼다. 알림은 서명 우편함과 몸의 내구 저장소, 마음의 정확한 문장 발화로 되살렸고 대화로 만드는 알림도 마음이 처리한다. 출력 장치·오디오 테스트·마이크 테스트·호출어 없는 대화 모드·몸 상태 표시도 새 몸 기준으로 되살렸다. 기준선 대비 새 실패 0, live NOT_RUN. 출처: Evelyn `docs/worklog/2026-10-29.md#evelyn-mind-consent-owner-20261030`.

재사용 가능한 교훈: 죽은 코드를 지우기 전에 "호출자가 없다"를 라우트 단위로 확인해야 한다. 같은 파일 안의 죽은 상태에 기대는 살아 있는 기능(동의 스위치)이 섞여 있고, 상태 채우는 쪽이 사라지면 그 기능은 테스트가 통과해도 조용히 항상 거부된다. 삭제 뒤에는 전체 회귀로 "새로 깨진 것"만 비교하고, 지운 함수를 이름으로 뽑아 쓰는 테스트 고정물(setUp)이 깨지는지 따로 봐야 한다. 또 한 프로세스가 다른 프로세스의 상태를 읽어야 할 때는 서명된 파일 한 장과 공용 판독 함수로 합의 기준(신선도·소유자·서명)을 한곳에 두면 소비자마다 어긋나지 않는다.

## Evelyn Mind 통합 브랜치 병합

감사 브랜치에 Mind 통합 브랜치를 병합했다. 삭제된 모듈을 건드린 감사 수리는 그 모듈의 삭제를 따르고, 살아 있는 선택기 수리와 그 테스트만 남겼다. 병합 뒤 전체 회귀가 통합 쪽 결과와 새 실패 0이고, 차이는 컷오버에서 이미 죽은 테스트 하나였다(source/offline).

재사용 가능한 교훈: 양쪽이 같은 파일을 다르게 바꾼 충돌은 "그 파일이 왜 지워졌나"부터 확인한다. 지운 쪽이 파이프라인 전체를 걷어낸 것이라면 수리 쪽 테스트는 대상이 사라진 것이라 함께 정리하고, 살아 있는 부분의 수리만 보존한다.

## Evelyn 첫 live 결함 사냥과 닥터

유닛 테스트가 전부 통과한 상태에서 실제 스택을 올리자 결함이 연달아 나왔다: 미고정 라이브러리 버전, 서버가 보고하는 이름과 다른 설정 이름, 201을 200으로 가정한 클라이언트, 재시작마다 무효가 되는 서명 파일, 세션에 없는 장치 이름, 그리고 느린 I/O를 수신 경로가 기다린 것. 각각을 실패 테스트로 고정하고 고친 뒤, 전부를 검사 항목으로 가진 진단 도구(닥터)를 만들었다.

재사용 가능한 교훈: (1) 페이크로 통과한 계약은 실제 서비스의 상태 코드·이름·버전으로 한 번은 대조해야 한다 — 계약 테스트의 페이크는 실제 응답을 그대로 베껴 쓴다. (2) 지연 문제는 "무엇이 무엇을 기다리는가"를 타임스탬프 두 줄(요청 로그와 저널)로 맞춰 보면 바로 드러난다. (3) 이미지 재빌드는 컨테이너 안의 소스로 확인하기 전까지 믿지 않는다.

## Evelyn 브라우저 소유자 확인창 제거

재기동마다 Windows 확인창 승인을 요구받던 것을 사용자 결정으로 없앴다. 런처가 매 기동 서명 비밀값을 새로 만들어 등록이 매번 무효가 되는 구조였다. 확인창만 빼고 서명·세대·쿠키·소유자 교체 규칙은 유지했으며, 소유자 신원은 body-local의 서명 상태에서 읽는다. live에서 자동 연결과 채팅 말풍선 표시를 확인했다.

재사용 가능한 교훈: 보안 단계를 없애 달라는 요청은 범위(최초 1회 유지 대 전면 제거)를 먼저 물어 결정으로 남기고, 없애더라도 그 단계가 지키던 나머지 불변식(서명, 일회성, 교체 거부)은 그대로 둔다. 감수하는 위험은 결정 문서에 적는다.

## Evelyn 결함 0 계획 1차

실패 테스트 732건을 먼저 분류(죽은 코드·환경·낡은 기대·진짜 결함·불명)하고 보니 확인된 진짜 결함은 0이었다. 그 사이 실제 환경에서는 기억 회상이 3~6초 걸리는 구조적 문제가 있었는데, 원인은 코드가 아니라 저장소 위치(Windows bind mount의 stat 비용)였고 Docker 볼륨으로 옮기자 26 ms가 됐다. 느린 것을 고장으로 보고하던 자기 모델, 마이크 없는 몸을 죽은 것으로 보던 런처도 "느림/저하"와 "고장/죽음"을 구분하지 않던 같은 종류의 결함이었다.

재사용 가능한 교훈: (1) 실패 테스트 수는 결함 수가 아니다 — 분류부터 하면 대부분 하네스·환경·낡은 기대다. (2) 성능 문제는 코드를 고치기 전에 실행 위치(파일시스템·커널 경계)를 바꾼 실측을 한 번 해 본다. (3) 상태 보고는 "저하"와 "불능"을 다른 값으로 둬야 상위(런처·Main·사용자)가 올바르게 반응한다. (4) 동시 쓰기가 있는 SQLite는 호스트와 컨테이너에 걸쳐 두지 않는다.

후속(같은 날 저녁): 테스트를 진실하게 고치자 소스 결함 5건이 드러났다(3.11에서 `wait_for`가 자식 태스크를 만들어 태스크 결속이 깨짐, 재시작마다 버전 증가, 미들웨어 뒤 본문 재스트림, 하드링크 오보고, CRLF가 바이트 해시 고정을 깸). 전체 회귀는 실패 548 → 8, 남은 8건은 모두 병렬 실행에서만 실패했다. 교훈: (5) 병렬 테스트에서만 나는 실패는 공유 자원부터 찾는다 — 기본 경로가 실제 체크아웃의 프로세스 간 잠금 파일이라 테스트 프로세스끼리 줄을 섰다. 프로세스마다 임시 경로를 주고, 실제 잠금을 다른 프로세스가 쥔 채로 통과·재현을 둘 다 확인한다. (6) `asyncio.sleep`을 전역 패치하는 테스트는 무관한 폴링까지 센다. (7) 시간 상한 단정이 실제로 재는 것이 무엇인지 본다 — 가짜 작업보다 실제 I/O가 빠르면 "재사용" 검사가 디스크 속도 측정이 된다. (8) 응답에 서명하는 계층은 응답을 바꾸는 계층보다 뒤에 있어야 한다(정규화 → 서명). (9) 안전 필터가 "전역 버전 일치"를 요구하면, 시스템이 매 턴 그 저장소에 쓰는 순간 필터를 통과하는 것이 없어진다 — 결속 단위는 의존하는 대상(노트)이어야 하고, 재구축이 그 이력을 지우지 않게 해야 한다. live에서 "같은 질문, 기억 쓴 답만 사라짐"으로 드러났다.
